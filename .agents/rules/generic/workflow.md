# 開発ワークフローの規律

global の哲学（コンテキスト最小化・単純化・Git First・テスト哲学）を、実際の進め方に落とす規律。

## 実装前

- **仕様確認**: 曖昧な仕様のまま実装しない。不明点は必ずユーザーに確認する。
- **前提の検証**: ユーザーが与えた前提や既存ドキュメントをそのまま信じない。コードを読み、必要ならコマンドを実行した結果を根拠に検証する。前提と実態が食い違う場合はコード・実行結果を優先し、ユーザーに指摘してから進める。
- **公開インターフェース保護**: 内部実装の追加は裁量で行う。**API・CLI・DBスキーマ・設定ファイル・ファイルフォーマット**の追加・変更・削除は必ずユーザーに確認する。
- **ブランチ + ワークツリー**: コードの変更を伴う作業はブランチを切り、`EnterWorktree` で独立したワークツリーに切り替えてから作業する。main へ直接コミットしない。main への変更はマージ経由のみ。

## 実装中

- **重複ロジック**: 同じ処理が複数箇所にないか確認する（抽象化は重複が実際に発生してから）。
- **段階的変更**: 大きな変更は小さく区切って進める。

## 実装後

- **テスト名**: 「条件」と「期待結果」を表現する（例: `fetchReturnsEmptyWhenNoDocuments`）。粒度の優先順位は 仕様テスト > 回帰 > E2E > ユニット > 実装依存。「呼ばれたか」「実行順」は検証しない。
- **サブエージェント活用**:
  - 監査レビュー: 大幅な変更・リファクタリング・効率化／簡略化の後は監査させ、結果を是々非々で判断する（単一ファイルでも該当）。監査には仕様（契約）と diff のみを渡し、「なぜ良いか」で結論へ誘導しない。問いは「この仕様を diff は満たすか・既存機能を壊さないか」。**ブランチ／ワークツリーを切った変更は、main へマージする前にこの監査を済ませる**（マージ後に回すのは漏れ。ブランチ高度＝レビューの品質ゲート）。監査は `advisor` ツール（Fable）を優先して使う。使えない場合は Opus サブエージェントにフォールバックする。
  - 並列化: 独立した複数タスク（影響範囲調査・テスト生成・実装分担など）は Agent ツールで並列実行する。
  - 実装委譲: 独立して切り出せる実装は Sonnet サブエージェントへ委譲する。
- **モデル選択**: 作業の性質に応じてモデルを使い分ける。

  | 作業 | モデル |
  |---|---|
  | ユーザーとの基本的なやり取り・設計判断・実装（本体） | Sonnet |
  | 判断の質が要る監査レビュー | Fable（`advisor` ツール）。使えない場合は Opus |
  | サブエージェントによる実装 | Sonnet |
  | 機械的な探索・並列調査 | Sonnet |

  表は「その作業を実行するモデル」を指定する。本体セッションが表の推奨モデルと異なる場合でも、対象作業は表通りのモデルへ委譲する。
- **レガシー候補の提示**: 不要と判断したものは削除せず候補として提示する。新規コード追加時は、同等以上の不要コードを削除できないか併せて検討する。

## 運用

- **検証の高度**: 品質ゲートは2つの高度にある。ブランチ高度（設計・保守性・重複＝レビュー）と統合／配布高度（フルビルド・回帰・E2E・配布物検証）。「ブランチ緑 ≠ 統合緑 ≠ 配布緑」を前提に、配布形態がある場合は配布物まで検証する（手順は `versioning.md`）。
- **レビュー**: 見直し・レビューを求められた場合、指摘事項は事実ベースのみ挙げる。問題がなければ「問題なし」と返す。無理に指摘を作らない。
