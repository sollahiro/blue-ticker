# iOSアプリ構想 — 立体的財務分析エクスプローラ

方向性のメモ。技術仕様・画面遷移の詳細設計はまだ行わない（`architecture.md`「デプロイモード」参照どおり iOS は将来クライアントとして既に見込み済み）。

## コンセプト

「財務分析を立体的に探索するアプリ」。

ウォーターフォールを一枚の図として表示するのではなく、**分析結果・推移・計算ロジックの3つの見方を、同じ分析対象に対して自由に行き来できる**ことを目指す。一般的な財務アプリの「グラフ画面 → 表画面 → 指標画面」という画面遷移中心の設計とは異なり、立方体を回すという単一の操作で視点が切り替わる。

Blue Ticker の強みは独自の分析ロジック（要因分解・正規化）にあるため、そのロジック自体を UI の中心に据える点が差別化になる。

## 立方体の3面

| 面 | 見せるもの | 問い |
|---|---|---|
| 正面 | 現在選択中の分析結果（例: 営業利益増減のウォーターフォール＝売上要因・利益率変化・販管費・その他・税金） | 何が起きたか |
| 側面 | 正面で選択中の項目の5年推移 | どう推移してきたか |
| 上面 | 正面で選択中の項目の計算ロジック（計算式または構成要素カード） | なぜその数字になったか |

3面は常に「同じ分析対象」を指している。正面で項目を選ぶ → 側面がその項目の5年推移に切り替わる。上面のカード（計算要素）を選ぶ → 側面がその要素の5年推移に切り替わる。

```
正面（結果）→ 項目選択 → 側面（推移）
     ↓
   上面（ロジック）→ 要素選択 → 側面（その要素の推移）
```

つまり「結果 → 計算要素 → その推移」という深掘りの流れを、画面遷移ではなく面の切り替えとして表現する。深掘りしても「何を見ているか」を見失いにくい構成が狙い。

## 操作フロー（企画書より）

1. 正面でウォーターフォールを見る
2. 気になる項目を選ぶ
3. 側面でその項目の5年推移を見る
4. 上面で計算ロジックを確認する
5. 構成要素を選ぶ
6. その要素の5年推移を見る

## リポジトリ配置

モノレポで問題ない。理由:

- iOS は REST `/v1` を叩くだけのクライアントで、`BlueTickerCore` / `BltServerCore` の SwiftPM ターゲット境界ルール（`CLAUDE.md`）の対象外。Xcode プロジェクトとして独立させれば、既存のターゲット依存規約と衝突しない
- API 契約（REST `/v1` が正）とクライアント実装を同じリポジトリに置くことで、エンドポイント変更時の追従漏れを防ぎやすい
- 認証まわり（iOS SSO・OIDC+PKCE）は roadmap に未着手項目として既に記録済み（`blt-server-roadmap.md`）

想定配置: `ios/`（または `apps/ios/`）配下に独立 Xcode プロジェクト。`swift build` / CI の対象には含めない（Xcode ビルドは別ワークフロー）。

## 機能taxonomyとの関係

機能群は「構造化 → 正規化 → 視覚化」の3層で再整理を検討中（詳細合意でき次第 `feature-tiers.md` に反映）。Cube は視覚化層のうち **Waterfall（financials の要因分解）の派生**と位置づける。Breakdown（事業別・地域別内訳）の立体化は Cube ではなく、Allocation（Sankey）側の iOS 拡張候補として別扱いにする方針。
