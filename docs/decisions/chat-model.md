# iOS チャット：AFM とサーバー LLM の振り分け

出典: 旧課題管理のチケット（移行日 2026-11-12）。当時の題名: 【コード】iOS チャット：AFM とサーバーLLMの振り分け、サーバーLLM API。
実装 Issue は GitHub [#699](https://github.com/sollahiro/blue-ticker/issues/699)。親（有報LAB API のアクセス制御）は [#696](https://github.com/sollahiro/blue-ticker/issues/696) / [#702](https://github.com/sollahiro/blue-ticker/issues/702)。
この文書は決定・契約の正本としてリポジトリで維持する。件数や進捗の最新値はここに書かない。

## 方針（2026-10-31 確認）

* 基本はサーバーLLMが回答する。
* AFMで答えられるものはAFMが答え、サーバーLLMの呼び出しを減らす（コスト削減策）。
* AFMが使えない端末では、すべてサーバーLLMで生成する。

## AFMに回すもの（案）

* 手元にある情報（概要、取得済みの数字、テーブル）の言い換えや短い説明。
* 既存APIを `Tool` で1〜2回呼べば答えられる質問（例: 特定年度の売上、株数）。

## サーバーLLMに回すもの（案）

* 有報本文など長文の読み込みや要約が要る質問。
* 複数社の比較、複数年にわたる推論。
* AFMが答えられなかった、または自信が低いと判断した質問。

## 振り分け方

* まずAFMが質問を分類する（`@Generable` で「端末で回答／サーバーへ」を返す）。サーバーへ回すときは、AFMの `Tool.call()` からHAPIS経由でサーバーLLM APIを呼ぶ。
* 振り分けの判定に迷ったらサーバーへ回す（品質を優先）。

## サーバーLLM API（2026-10-31 方針）

* モデルは OpenRouter 経由で呼ぶ。
* 呼び出しは HAPIS の Worker から OpenRouter へ直接行う。iOS → HAPIS ゲートウェイ（App Attest のセッションで認証）→ OpenRouter の順。Fly は使わず、有報本文を Neon から読んでプロンプトを組み立てるような重い処理が必要になったら、そこだけ Fly に分ける。
* 応答はストリーミング（SSE）で返す。
* OpenRouter の API キーはサーバー側に1つだけ置く。端末には出さない。
* 数字はサーバー側でもコードで計算して渡し、LLMには文章化だけをさせる。
* モデルは `anthropic/claude-haiku-5.5`（2026-10-31 決定。OpenRouter 上で入力 $0.10／出力 $0.50 per 1M tokens、文脈 1M）。
* モデル名と切り替え先はコードに直書きせず、Worker の環境変数（または設定）で持ち、いつでも差し替えられるようにする。
* OpenRouter の `models` 指定で切り替え先を並べ、障害時に自動で切り替える。切り替え先の候補は `google/gemini-3.1-flash-lite`。
* 振り分けは OpenRouter の自動ルーティング（`openrouter/auto`）は使わず、AFM の分類結果をもとに HAPIS が呼ぶモデルを決める（コストを読めるようにするため）。
* heavy tier には入れない（2026-10-31 決定）。チャットは専用の「AI回答」区分で回数とトークンを数える。

## 使用量の管理

* ユーザーごとのキーは作らず、HAPIS で App Attest の端末キーIDごとに LLM の呼び出し回数とトークン数を数える。
* 料金体系（外部公開API）: Guest（アカウントなし）→ Free（アカウントあり）→ Paid（Starter→Standard→Premium。三分割するかは要検討）。Guest と Free では使えるエンドポイントに差をつける予定。
* iOS ユーザーはアカウント登録不要だが、App Attest で端末が確認できているので **Free 相当**として扱う（2026-10-31）。
* 端末ごとの LLM 上限（Free、2026-10-31 改定）: 1日10回、1日3万トークン、1分5回。Paid 導入時に Free を下げると改悪になるため、最初から低めにしておく。超えたらサーバーLLMは断り、「クラウドの高性能モデルの上限に達しました。ここからはデバイス上の標準モデルで続けます。上限は明日リセットされます」と表示する（2026-10-31 文言決定。画面には「AFM」という語を出さない）。AFM が使えない端末では「クラウドの高性能モデルの上限に達しました。上限は明日リセットされます」のみ。
* この上限は外部APIの Free と共通にする（2026-10-31 決定）。
* Free ユーザー1人あたりの最大コスト（Haiku 5.5）: 現実的には月約 $0.15（約 $0.0005 × 10回 × 30日）。毎日3万トークンを使い切っても月約 $0.16（約25円、入力8：出力2）。
* Paid（iOS 課金、月400円・Starter、2026-10-31 決定）: 1日30回、1日10万トークン。最悪でも月約80円。粗利50%死守が条件で、手数料30%でも200円（50%）、15%なら260円（65%）残る。複数端末は `originalTransactionId` 単位で共有。
* **ツール呼び出しの制限（2026-10-31 決定）**: サーバーLLMのツールは HAPIS Worker が実行するので、プランごとに渡すツール・回数・返す量をサーバー側で制御する。重いエンドポイントを頻繁に叩かれないようにするのが目的。

  | 項目 | Free | Paid（400円） |
  | -- | -- | -- |
  | 軽いツール（`overview`・`financials`・`shares`・`breakdown`・同業種） | 可 | 可 |
  | `filing-content` | 抜粋のみ（1回、約4,000トークンまで） | 1回の回答で2回まで、1回約8,000トークンまで |
  | `statement` | 不可 | 1回の回答で1回まで |
  | 1回の回答のツール呼び出し | 合計3回まで | 合計6回まで |
  | 1回の回答の入力上限（ツール結果込み） | 約1万トークン | 約2万トークン |
  * 上限に達したら集めた情報で回答し、Free では「詳しい本文の読み込みは Paid で使えます」と添える。
  * ツール結果も入力トークンとして1日の上限に数える。
  * 値は使われ方を見て調整する（使えなさすぎても意味がない）。設定で持つ。
  * AFM がツールで叩く API は通常のゲートウェイ経由なので、エンドポイント×Tier の区分ごとの上限がそのまま効く。
  * AFM が使えない端末は全質問がサーバーLLMに回り、1日10回を早く使い切る。これは仕方ないものとして許容する（2026-10-31 決定、特別扱いはしない）。
* 上限値もモデル名と同じく設定で持ち、コードを変えずに調整できるようにする。
* AFMで答えた分は数えない。
* 安全策として、OpenRouter 側でもそのキーに月の利用上限を設定する（まずは月 $20 程度）。HAPIS の制限が不具合ですり抜けても、請求がその額で止まる。
* 課金の実装（StoreKit のサブスク、購入記録の検証）は今回の範囲外。必要になったら別 Issue にする。値だけ先に決めておく。

## 完了条件

* 同じ質問に対して、AFMありの端末となしの端末で、同じ数字の回答が返る。
* AFMで処理した割合を計測できる（コスト削減効果の確認用）。
